# Live Clip

รับสัญญาณไลฟ์ SRT จาก vMix / Wirecast นอกสถานที่ เก็บเป็นบัฟเฟอร์ย้อนหลังบนเซิร์ฟเวอร์
ให้ทีมตัดเปิดดูในเบราว์เซอร์ระหว่างไลฟ์ ตั้งจุด In/Out แล้วได้คลิป MP4 ไปตัดต่อด้วยโปรแกรมอะไรก็ได้
คลิปที่ตัดแล้วเก็บขึ้น Wasabi

```
vMix / Wirecast ──SRT (UDP 8890, มี passphrase)──▶ MediaMTX ──▶ dvr.sh (ffmpeg)
                                                                 │ บัฟเฟอร์ HLS ไฟล์ละ 2 วิ
                                                                 ▼
                         เบราว์เซอร์ทีมตัด ◀── web (app.py) ──▶ ffmpeg ตัดคลิป ──▶ Wasabi
```

- **บัฟเฟอร์อยู่บนดิสก์เซิร์ฟเวอร์เท่านั้น** ไม่ขึ้น Wasabi เพราะ Wasabi คิดเงินขั้นต่ำ 90 วันต่อไฟล์
  บัฟเฟอร์ที่เขียนแล้วลบทุกไม่กี่ชั่วโมงจะโดนคิดเงินเต็ม 90 วันทุกไฟล์
- **ขึ้น Wasabi เฉพาะคลิปที่ตัดแล้ว** ลิงก์ดาวน์โหลดสร้างใหม่ทุกครั้งที่กด จึงไม่มีวันหมดอายุในหน้าเว็บ
- **คลิปโหลดจากเซิร์ฟเวอร์ได้ทันที** ตั้งแต่ตัดเสร็จ ไม่ต้องรออัป Wasabi
  ถ้าอัปพลาด คลิปจะขึ้นว่า "ล้มเหลว" พร้อมสาเหตุ ยังโหลดจากเซิร์ฟเวอร์ได้ และกด "ลองใหม่" ได้

## สิ่งที่ต้องเตรียมก่อนขึ้นใช้งานจริง

| เรื่อง | ใครทำ | รายละเอียด |
|---|---|---|
| เครื่องที่จะรัน | นัท | โฮสต์ Docker ตัวไหนก็ได้ ดิสก์ว่างพอสำหรับบัฟเฟอร์ ดูตารางด้านล่าง |
| เปิดพอร์ต | IT | forward **UDP 8890** จากอินเทอร์เน็ตเข้าเครื่องนี้ |
| โดเมน + HTTPS | นัท | ชี้โดเมนผ่าน Nginx Proxy Manager มาที่พอร์ตเว็บ 8080 |
| Wasabi | นัท | สร้าง bucket ใน region ap-southeast-1 Singapore + access key ชุดใหม่ที่เขียนได้เฉพาะ bucket นี้ |
| Wasabi lifecycle | นัท | เปิด "Delete incomplete multipart uploads" ไว้ กันชิ้นอัปค้างโดนคิดเงิน |
| passphrase SRT | นัท | สุ่ม 32–64 ตัวอักษร ห้ามเกิน 79 เพราะ MediaMTX รับได้แค่นั้น แต่ vMix/Wirecast รับได้ 80 |
| รหัสอื่น ๆ | นัท | `WEB_PASSWORD` 12 ตัวขึ้นไป และ `MEDIAMTX_API_PASS` สุ่มจากตัวอักษรอังกฤษกับตัวเลข ใช้คุยกันระหว่างสองคอนเทนเนอร์ |

พื้นที่ดิสก์ที่บัฟเฟอร์ใช้ คิดที่ 10 Mbps:

| ย้อนดูได้ | 1 สัญญาณ | 2 สัญญาณ | 4 สัญญาณ |
|---|---|---|---|
| 1 ชม. | 4.5 GB | 9 GB | 18 GB |
| 2 ชม. | 9 GB | 18 GB | 36 GB |
| 6 ชม. | 27 GB | 54 GB | 108 GB |

บัฟเฟอร์ของไลฟ์ที่จบแล้วจะอยู่ต่อตามค่า "เก็บหลังจบไลฟ์" แล้วลบเอง
ถ้าดิสก์ว่างต่ำกว่า `MIN_FREE_GB` ระบบจะลบบัฟเฟอร์ของไลฟ์ที่จบแล้วก่อนเวลา โดยเริ่มจากเก่าสุด
และขึ้นแถบเตือนในหน้าเว็บว่าลบรอบไหนไป ระบบจะไม่ลบบัฟเฟอร์ของไลฟ์ที่กำลังสด
และไม่ลบรอบที่สัญญาณเพิ่งหลุดไม่ถึง `RECONNECT_MIN` นาที เพราะตัวส่งอาจต่อกลับมา

โหมดเก็บคลิปในเครื่อง คือไม่ได้ตั้ง Wasabi คลิปจะไม่ถูกลบอัตโนมัติเลย เพราะเป็นสำเนาเดียว ต้องลบเอง

## รันในเครื่อง (ทดสอบ)

```bash
cp .env.example .env      # แล้วกรอกค่าจริง
docker compose up -d --build
```

`docker-compose.yml` build อิมเมจทั้งสองตัวจากโฟลเดอร์นี้ ค่าตั้ง MediaMTX กับ dvr.sh ถูกอบไว้ในอิมเมจ
แก้ไฟล์ใน `mediamtx/` แล้วต้อง `up -d --build` ใหม่

## ขึ้น Portainer (เครื่องจริง)

โฮสต์คือ NAS RackStation ตัวเดียวกับ probook มี Docker, Nginx Proxy Manager (stack `management`) และดิสก์ว่างหลายสิบ TB

1. **โค้ดอยู่ในรีโป GitHub `narasitk77/live-clip`** ทุก push ขึ้น `main` จะ build อิมเมจ 2 ตัวขึ้น GHCR
   คือ `live-clip-web` และ `live-clip-mediamtx` แท็ก `latest` และ `sha-<commit>`
2. **stack ใน Portainer** ชื่อ `live-clip` (id 156, สร้าง 26 ต.ค. 2026) แบบ git-backed ชี้รีโปนี้ compose path = `docker-compose.portainer.yml`
   env ของ stack มาจากไฟล์ `.env.portainer` บนเครื่องนัท (ไม่ขึ้น git, มี `IMAGE_TAG=sha-<commit>`, รหัสทุกตัว,
   `SRT_PUBLIC_HOST=thestandard.fortiddns.com`, `MIN_FREE_GB=200`, `CUT_WORKERS=1` และค่า S3 ถ้ามี)
   สร้าง/ปรับด้วย `python3 scripts/portainer_stack.py create|redeploy <tag>|status|logs` สคริปต์เช็กว่าคอนเทนเนอร์รันแท็กที่ขอจริง
3. **เว็บไม่เปิดพอร์ตบนโฮสต์** NPM อยู่บนเครือข่าย `management_default` เดียวกัน (ทดสอบแล้วว่า NPM เรียก `live-clip-web:8080` ถึง)
   หลัง IT เพิ่ม DNS `liveclip.thestandard.co` แล้ว ให้เพิ่ม Proxy Host ใน NPM ตามนี้

   | ช่อง | ค่า |
   |---|---|
   | Domain Names | liveclip.thestandard.co |
   | Scheme | http |
   | Forward Hostname / IP | live-clip-web |
   | Forward Port | 8080 |
   | Block Common Exploits | เปิด |
   | Websockets Support | ไม่ต้อง |
   | SSL | ขอ Let's Encrypt ใหม่ หรือใช้ใบเดียวกับ probook ถ้าเป็น wildcard, เปิด Force SSL |

   วง LAN ของ NAS (192.168.21.x) เข้าจากวงออฟฟิศไม่ได้ จึงไม่มีทางลัดก่อนมีโดเมน
   ตรวจ: `curl -su editor:<รหัส> https://liveclip.thestandard.co/api/state` ต้องได้ JSON ที่มี `"storage": "local"`
4. **IT ต้อง forward UDP 8890 และ UDP 8891** จาก FortiGate มาที่ NAS 8890 = vMix/OBS (ตั้งชื่อสัญญาณเองได้หลายตัว), 8891 = Wirecast
5. **deploy รอบถัดไป** = push ขึ้น main รอ CI เสร็จ (`gh run watch`) แล้ว `python3 scripts/portainer_stack.py redeploy sha-<commit>`
   คำสั่งนี้ส่ง env จาก `.env.portainer` ไปด้วยทุกครั้ง จึงใช้เปลี่ยนรหัสหรือเปิด Wasabi ได้ด้วย
   กับดักเดียวกับ probook คือ redeploy โดยไม่เปลี่ยน IMAGE_TAG จะได้อิมเมจเดิม
6. **ทดสอบว่าพอร์ตเปิดถึงแล้ว** รัน `test/probe_prod.sh` จากเครื่องไหนก็ได้ที่มี Docker แล้วดู `logs mediamtx`
   ต้องเห็น `publishing to path 'probe1'` ถ้าขึ้น I/O error แปลว่า UDP 8890 ยังมาไม่ถึง NAS (26 ต.ค. ยังไม่ถึง)

ยังไม่ตั้ง Wasabi ก็ขึ้นได้ ระบบจะเก็บคลิปไว้บน NAS อย่างเดียว ใส่ค่า S3 ทั้งสี่ตัวแล้ว redeploy เมื่อไหร่ก็เปลี่ยนเป็น Wasabi

- **หน้าเว็บ** ผูกกับ `127.0.0.1` ของเครื่องเท่านั้น เข้าจากเครื่องอื่นตรง ๆ ไม่ได้ ต้องผ่าน HTTPS ของ Nginx Proxy Manager
  ห้ามตั้ง `WEB_BIND` เป็น `0.0.0.0` เพราะรหัสผ่านจะวิ่งเป็น HTTP เปล่า
- **ล็อกอิน** ใช้ `WEB_USER` / `WEB_PASSWORD`
- **ค่าบังคับ** ถ้ารหัสไม่ครบ ยังเป็นค่าตัวอย่าง หรือตั้ง Wasabi ไม่ครบทั้งสี่ค่า ระบบจะไม่ยอมเริ่มและบอกว่าขาดอะไร
- **โหมดเก็บในเครื่อง** ถ้าปล่อยค่า S3 ว่างทั้งหมด แอปจะเก็บคลิปไว้บนเซิร์ฟเวอร์อย่างเดียว
- **endpoint ของ Wasabi** ต้องตรงกับ region ของ bucket ถ้าผิด region อ่านไฟล์ได้แต่เขียนไม่ได้ อาการนี้หลอกว่าระบบปกติ

## ตั้งค่าตัวส่ง

ทั้งสองโปรแกรมใช้ค่าชุดเดียวกัน

| ช่อง | ค่า |
|---|---|
| โหมด | Caller |
| Address / Hostname | ที่อยู่สาธารณะของเซิร์ฟเวอร์ ค่า `SRT_PUBLIC_HOST` |
| Port | 8890 |
| Stream ID | `publish:<ชื่อสัญญาณ>` เช่น `publish:cam1` ใช้ตัวเล็ก ตัวเลข `-` `_` ยาวไม่เกิน 32 ตัว |
| Passphrase | ค่า `SRT_PASSPHRASE` |
| วิดีโอ | H.264 เท่านั้น ห้าม HEVC เพราะเบราว์เซอร์เล่นไม่ได้ทุกตัว |
| เสียง | AAC สเตอริโอ แทร็กเดียว ใน vMix ห้ามเปิด "Split Stereo Pairs into Separate Tracks" |
| Keyframe | ทุก 1–2 วินาทีแบบคงที่ ใน vMix คือช่อง "Keyframe Frequency (seconds)" |
| Bitrate | ถ้าอัปโหลดหน้างานได้ 10 Mbps ให้ตั้งรวมราว **6 Mbps** เพราะ SRT ต้องเผื่อส่งซ้ำอีกราว 25% |

- **vMix** ตั้งที่ Settings > Outputs > ปุ่มฟันเฟือง > SRT ช่อง Latency ให้ตั้ง 500–1000 ms สำหรับเน็ตในประเทศ
  ค่านี้ฝั่งเซิร์ฟเวอร์ใช้ตามที่ vMix ส่งมา ช่อง Key Length ตั้ง 16, 24 หรือ 32 ก็ได้
- **Wirecast** ตั้งที่ Output > Output Settings > SRT แต่ให้ส่งเข้า **พอร์ต 8891** แทน 8890 และไม่ต้องใส่ Stream ID
  เพราะ Wirecast ไม่มีช่องตั้ง latency พอร์ต 8891 คือตัวรับแยก (`relay-wirecast`) ที่เราตั้ง latency ให้เอง
  ค่าเริ่มต้น 1000 ms (`WIRECAST_LATENCY_MS`) สัญญาณจะโผล่ในหน้าเว็บชื่อ `wirecast1` (`WIRECAST_NAME`)
  ตัวรับนี้รับ Wirecast ได้ทีละเครื่อง ถ้ามีเครื่องที่สองให้ก๊อปบล็อก `relay-wirecast` ใน compose เป็นพอร์ต 8892 และชื่อใหม่

ถ้าส่งชื่อเดียวกันจากสองเครื่องพร้อมกัน เครื่องหลังจะเตะเครื่องแรกออก ดังนั้นต้องตั้งชื่อสัญญาณไม่ซ้ำกันต่อเครื่อง

## ขึ้นคลาวด์ (ทางเลือกแทน NAS)

ชุดเดียวกันรันบน VM คลาวด์ได้ ไม่ต้องพึ่ง FortiGate หรือ DNS ของบริษัท ใช้ `docker-compose.cloud.yml` ซึ่งเพิ่ม Caddy
ทำ HTTPS ให้อัตโนมัติ ถ้าไม่มีโดเมนใช้ชื่อ `<ip-คั่นด้วยขีด>.sslip.io` ได้ทันที

1. สร้าง VM Ubuntu ที่ Singapore ขนาด 2 vCPU / 4 GB ขึ้นไป (DigitalOcean, Vultr, Hetzner ตัวไหนก็ได้) เปิด firewall UDP 8890, UDP 8891, TCP 80, TCP 443
2. บน VM รัน `curl -fsSL https://raw.githubusercontent.com/narasitk77/live-clip/main/cloud/setup.sh | sh`
   สคริปต์ติดตั้ง Docker, โคลนรีโป, สุ่มรหัสลง `/opt/live-clip/.env` และบอกชื่อเว็บที่จะได้
3. `cd /opt/live-clip && docker compose up -d` แล้วเปิด `https://<ชื่อที่สคริปต์บอก>`
   (`COMPOSE_FILE` ใน `.env` เป็นตัวเลือกไฟล์ compose ห้ามใส่ `-f` เอง เพราะบนเครื่องแบบ RTMP จะทิ้ง `docker-compose.rtmp.yml` แบบเงียบ ๆ)
   ถ้าจะรับ RTMP ด้วย ให้ใช้ `cloud/rtmp-setup.sh` แทนข้อ 2–3 ดู [docs/runbook-cloud-rtmp.md](docs/runbook-cloud-rtmp.md)
4. ใส่ค่า Wasabi ใน `.env` แล้ว `up -d` ใหม่ เพื่อให้คลิปไปอยู่บน Wasabi (ดิสก์ VM เล็ก ควรทำ)

ค่าใช้จ่ายโดยประมาณ: VM ราว 700–1,500 บาท/เดือน; แบนด์วิดท์ที่กินคือคนดูสดผ่านเว็บ ราว 4.5 GB ต่อคนต่อชั่วโมงที่ 10 Mbps
(VM ส่วนใหญ่ให้ 2–4 TB/เดือน) และ Wasabi ขั้นต่ำ 1 TB ราว 280 บาท/เดือน

## วิธีใช้ (ทีมตัด)

1. เลือกสัญญาณทางซ้าย จุดเขียวแปลว่ารับสัญญาณอยู่ จุดแดงแปลว่ากำลังบันทึกบัฟเฟอร์
2. เลื่อนแถบเวลาย้อนดู หรือกด "ไปที่สด" ช่อง "ดูช้ากว่าสด" ใช้ดูตามหลังสดตามจำนวนวินาทีที่ตั้ง
3. กด `I` ตั้งจุดเริ่ม กด `O` ตั้งจุดจบ แล้วปรับละเอียดด้วยปุ่ม ±1 วิ และ ±0.1 วิ ปุ่ม "ไปดู" พาไปเช็กภาพตรงจุดนั้น
4. ตั้งชื่อ เลือกโหมด แล้วกด "สร้างคลิป"
   - **เร็ว** ไม่เข้ารหัสใหม่ เสร็จในไม่กี่วินาที คลิปอาจเริ่มก่อน In ไม่เกินราว 2 วินาที แต่ไม่มีวันเริ่มช้ากว่า In
   - **ตรงเฟรม** เข้ารหัสใหม่ เริ่มและจบตรงเฟรม ช้ากว่าและกิน CPU เซิร์ฟเวอร์
5. กด "ดาวน์โหลด" ในรายการคลิป

ถ้าสัญญาณหลุดแล้วต่อกลับภายใน 10 นาที ระบบจะต่อรอบเดิมให้ คลิปที่คร่อมช่วงสัญญาณขาดจะบอกว่าภาพขาดไปกี่วินาที
ตรงจุดต่อกลับ ภาพจะค้างราว 2 วินาทีขณะที่เสียงเดินต่อ เพราะเสียงมาถึงก่อนภาพ keyframe แรก
โหมดตรงเฟรมเติมเฟรมซ้ำให้ ไฟล์จึงเป็น frame rate คงที่ ใช้กับ Premiere ได้

### Replay: ส่งรอบที่จบแล้วออกไลฟ์อีกครั้ง

เซิร์ฟเวอร์ส่งเองด้วย ffmpeg (`-re -c copy` แบบเดียวกับ OBS เล่นไฟล์) ไม่ต้องเปิด OBS และไม่ใช้เน็ตของออฟฟิศ

1. เลือกรอบที่จบแล้วทางซ้าย ถ้าจะส่งเฉพาะบางช่วง ให้ตั้ง In/Out ไว้ ถ้าไม่ตั้งจะส่งทั้งรอบ
2. เปิดการ์ด "Replay" เลือก YouTube / Facebook หรือใส่ Server เอง แล้วใส่ Stream key แบบเดียวกับใน OBS
3. ติ๊ก "วนซ้ำจนกดหยุด" ถ้าต้องการให้วน แล้วกด "เริ่มส่ง" สถานะจะขึ้นในตาราง Replay พร้อมปุ่มหยุด

เรื่องที่ควรรู้:
- **ไม่เข้ารหัสใหม่** ภาพเท่าต้นฉบับและแทบไม่ใช้ CPU จุดเริ่มและจุดจบจะตรงรอยต่อท่อน คลาดไม่เกินท่อนละ 2–4 วินาที และช่วงที่สัญญาณขาดจะถูกข้าม
- **Stream key** ไม่ถูกบันทึกลงดิสก์ ไม่ลง log และไม่ส่งกลับมาที่หน้าเว็บ ถ้าแอปรีสตาร์ท replay จะหยุดและขึ้นว่าล้มเหลว ต้องกดเริ่มใหม่และใส่ key อีกครั้ง
  ระหว่างส่ง key อยู่ในคำสั่ง ffmpeg คนที่เข้าเครื่องหรือ Portainer แล้วเปิดดู process list จะเห็น (คนกลุ่มเดียวกับที่อ่าน .env ได้อยู่แล้ว)
- **สถานะ** "กำลังเชื่อมต่อ" จนกว่าปลายทางจะรับและภาพเริ่มออกจริง แล้วจึงเป็น "กำลังส่ง" (ffmpeg รายงานตำแหน่งที่ส่งออกไปแล้ว)
  ถ้าปลายทางรับสายแต่ไม่แสดงผล (เช่นไลฟ์ใน YouTube Studio ถูกปิดไปแล้ว) ระบบมองไม่เห็น ให้เปิดดูที่ปลายทางด้วยทุกครั้ง
- **ปลายทาง** ต้องเป็นที่อยู่บนอินเทอร์เน็ต ระบบปฏิเสธเครื่องในวงภายใน (docker, LAN, 127.0.0.1) ถ้าจำเป็นต้องส่งเข้าเครื่องในออฟฟิศ ให้ใส่ชื่อนั้นใน `REPLAY_ALLOW_HOSTS`
- **วนซ้ำ** ใช้การเชื่อมต่อเดียวตลอด (ไม่ตัดแล้วต่อใหม่ทุกรอบ) และหยุดเองเมื่อส่งครบ `REPLAY_MAX_HOURS` (ค่าเริ่มต้น 12 ชม.) กันลืมปิดจนกินโควตาเน็ตของ VM
- **รอบที่เครื่องส่งต่อเข้ามาใหม่ด้วยค่าภาพ/เสียงต่างจากเดิม** ส่งรวดเดียวไม่ได้ ระบบจะบอกเวลาที่เปลี่ยน ให้ตั้ง In/Out แยกช่วง
- **key ยาว** key ถูกส่งแยกจาก URL (ffmpeg ตัด URL ที่ยาวเกินราว 1,000 ตัวอักษรทิ้งเงียบ ๆ) key แบบ TikTok ยาวได้ถึง 4,096 ตัวอักษร
- **ล้มเหลว** ถ้าส่งไม่ขึ้นตั้งแต่ครั้งแรก มักเป็นเพราะ key ผิดหรือปลายทางยังไม่เปิดรับไลฟ์ ถ้าสายหลุดกลางทาง ระบบจะต่อใหม่จากจุดเดิมเอง แต่ถ้าปลายทางปฏิเสธ 3 ครั้งติดจะหยุดและแจ้ง
- **"หยุดเองเมื่อเวทีนี้กลับมาไลฟ์"** (ติ๊กไว้เป็นค่าเริ่มต้น) ใช้กันไม่ให้ replay กับไลฟ์จริงส่งเข้า key เดียวกันจนเตะกันเอง ถ้าติดต่อ MediaMTX ไม่ได้ ระบบจะไม่หยุด replay
- **ส่งพร้อมกันได้ไม่เกิน `REPLAY_MAX` ช่อง** (ค่าเริ่มต้น 2) แต่ละช่องกินเน็ตขาออกเท่าบิตเรตของเวที (ราว 6–8 Mbps)
- **รอบที่ถูกลบตามเวลา "เก็บหลังจบไลฟ์"** ถ้ามี replay กำลังส่งรอบนั้นอยู่ จะส่งต่อได้จนกดหยุด เพราะท่อนที่ใช้ถูก hard-link แยกไว้ แต่ต้องเริ่ม replay ก่อนที่รอบจะถูกลบ

### Restream: ส่งเวทีสดออกหลายแพลตฟอร์มพร้อมกัน

เครื่องส่งของเวทีส่งเข้าเซิร์ฟเวอร์ครั้งเดียว แล้วเซิร์ฟเวอร์ส่งต่อให้สูงสุด 4 ช่องพร้อมกัน (เช่น YouTube public, YouTube private,
Facebook, TikTok) โดยไม่เข้ารหัสภาพใหม่ แต่ละช่องเป็น ffmpeg แยกตัว ช่องหนึ่งมีปัญหาไม่กระทบช่องอื่น

**ตั้งครั้งแรก (ผู้ดูแล)**
- ตั้ง `RESTREAM_PIN` ใน `.env` (12 ตัวขึ้นไป ห้ามเป็นตัวเลขล้วน) ถ้าไม่ตั้ง ฟีเจอร์นี้ปิด ทุกคำสั่งของ Restream ต้องใส่ PIN นี้
  เพิ่มจากรหัสเข้าเว็บ เพราะรหัสเข้าเว็บแชร์กับเครื่องตัดต่อทุกเครื่อง ส่วน stream key ของช่องจริงถูกเก็บไว้บนเซิร์ฟเวอร์
- MediaMTX ต้องให้ผู้ใช้ `liveclip` มีสิทธิ์ `read` และเปิด `rtsp: yes` (อยู่ใน `cloud/rtmp/mediamtx.yml` แล้ว)
  ไฟล์นี้แก้ตอนมีเวทีไลฟ์ไม่ได้ ให้ deploy ตอนไม่มีเวทีไลฟ์ ตอนนี้ Restream ใช้ได้เฉพาะชุดคลาวด์ที่ใช้ไฟล์นี้
  (`docker-compose.cloud.yml` + `docker-compose.rtmp.yml`) ชุด NAS และชุดรันในเครื่องใช้ค่าตั้งที่ฝังในอิมเมจ ซึ่งยังไม่ให้สิทธิ์ `read`
  ถ้ากดเริ่มที่นั่น แถวจะขึ้นว่าอ่านสัญญาณเวทีจาก MediaMTX ไม่ได้
- `MEDIAMTX_API_PASS` ต้องเป็นตัวอักษรอังกฤษ ตัวเลข หรือ `. _ ~ -` เท่านั้น เพราะ Restream ใช้รหัสนี้อ่านสัญญาณเวที (แอปจะไม่ยอมเริ่มถ้าไม่ใช่)
- ถ้าเคยเปิด YouTube push แบบเก่า (`cloud/set-youtube-key.sh`) ของเวทีนั้นไว้ ต้องปิดก่อน (`--off`) ไม่อย่างนั้น Restream จะไม่ยอมเริ่ม

**ใช้งาน (คนคุมไลฟ์)**
1. เปิดการ์ด "Restream" เลือกเวที กด "+ เพิ่มปลายทาง" ใส่ชื่อช่อง Server และ Stream key ทำล่วงหน้าได้ ไม่ต้องรอเวทีไลฟ์
   ถ้าเวทีนั้นยังไม่เคยมีสัญญาณเข้าเลย กด "+ เวที" แล้วพิมพ์ชื่อเวทีให้ตรงกับที่เครื่องส่งใช้ PIN จะถูกถามใหม่ทุกครั้งที่โหลดหน้าเว็บ
2. ตั้งค่าที่แพลตฟอร์มให้พร้อมรับ ตามรายการด้านล่าง
3. เมื่อเวทีมีสัญญาณแล้ว กด "เริ่มส่ง" ทีละช่อง หรือ "เริ่มส่งทุกช่อง" หน้าต่างยืนยันจะบอกชื่อเวที บิตเรตที่รับอยู่ และช่องที่จะส่ง
4. ดูสถานะรายช่อง แล้ว **เปิดดูที่แพลตฟอร์มทุกช่องว่าไลฟ์ขึ้นจริง**
5. จบรายการ: กดจบไลฟ์ที่แพลตฟอร์มก่อน แล้วกด "หยุดทุกช่อง" ที่นี่

**ตั้งค่าที่แพลตฟอร์ม**
- **YouTube** ปิด Auto-stop (ไม่อย่างนั้นสัญญาณหลุดราว 1 นาทีรายการจะจบและลิงก์เปลี่ยน) แนะนำปิด Auto-start ด้วย
  ภาพจะเข้าแค่ preview จนกด Go Live ใน Studio จึงไม่มีอะไรออกอากาศเองโดยไม่ตั้งใจ จบรายการต้องกดจบใน Studio
- **Facebook** ใช้ persistent stream key ได้ แต่ต้องกด Go live ใน Live Producer เองทุกงาน ปิดตัวเลือกจบไลฟ์เมื่อสัญญาณหยุด
  ถ้าสัญญาณขาดเกิน 2–3 นาที ไลฟ์เดิมจะจบ ต้องสร้างไลฟ์ใหม่ ไลฟ์ได้ไม่เกิน 8 ชม.
- **TikTok** Server URL กับ key ใหม่ทุกไลฟ์ ต้องกดสร้างในหน้า Go LIVE ของ TikTok แล้วแก้ช่องนี้ วางค่าใหม่ และเริ่มส่งภายในไม่กี่นาที
  ปิด "End LIVE if stream stops" เลือก Screen adaptation = Original ถ้าไม่อยากโดนครอปด้านข้าง ห้ามมี QR หรือโลโก้แพลตฟอร์มอื่นบนภาพ
  หยุดส่งแล้วต้องกดจบห้องที่ TikTok ด้วย TikTok ไม่มีโหมดไลฟ์ส่วนตัว การทดสอบจึงออกสาธารณะเสมอ

**สถานะหมายถึงอะไร** ระบบรู้แค่ว่าเซิร์ฟเวอร์ของแพลตฟอร์มรับสัญญาณและข้อมูลกำลังออกไป ไม่รู้ว่าคนดูเห็นหรือยัง จึงไม่มีคำว่า "ออกอากาศ"
| สถานะ | ความหมาย |
|---|---|
| กำลังเชื่อมต่อ | ffmpeg เริ่มแล้ว แต่ภาพแรกยังไม่ออก ถ้าเกิน 30 วินาทีจะตัดแล้วลองใหม่ |
| ส่งถึงปลายทางแล้ว | แพลตฟอร์มรับสัญญาณ และมีข้อมูลออกไปภายใน 6 วินาทีล่าสุด (มีตัวเลข Mbps) |
| ไม่มีข้อมูลออก | ffmpeg ยังอยู่แต่ไม่มีอะไรออกไปแล้ว ครบ 20 วินาทีจะตัด |
| ช่องนี้หลุด กำลังต่อใหม่ | เวทียังส่งอยู่แต่ช่องนี้หลุด (ปลายทางตัด หรือเซิร์ฟเวอร์อ่านสัญญาณเวทีไม่ได้ ข้อความในแถวจะบอก) ต่อใหม่เองที่ 2, 5, 10, 20, 30 วินาที |
| รอสัญญาณเวที | เครื่องส่งของเวทีหลุดหรือไม่ส่งภาพ ทุกช่องรอ ไม่ยิงแพลตฟอร์มซ้ำ และส่งต่อเองเมื่อภาพกลับมา |
| ระบบหยุดส่งเอง | เวทีหายเกิน `RECONNECT_MIN` (10 นาที) จึงปลดช่องให้ ถ้ายังออกอากาศอยู่ต้องกดเริ่มใหม่ |
| ล้มเหลว | ส่งไม่ขึ้นตั้งแต่แรก 2 ครั้ง (มักเป็น key ผิดหรือปลายทางยังไม่เปิดรับ) หรือส่งให้นิ่งเกิน 30 วินาทีไม่ได้เลยมา 5 นาที |

ช่องที่ล้มเหลว ถูกระบบหยุดเอง รอเวทีนานเกิน 1 นาที หรือส่งให้นิ่งไม่ได้มาเกิน 30 วินาที (รวมกรณีหลุด ๆ ติด ๆ) จะขึ้นในแถบเหลืองบนสุดของหน้าเว็บทุกคน
และ "เหตุการณ์ล่าสุดของเวทีนี้" ในการ์ดเก็บว่าเกิดอะไรขึ้นเมื่อไร (ไฟล์เต็มอยู่ที่ `/data/restream/<เวที>.log`)

**เรื่องที่ควรรู้**
- **ไม่เข้ารหัสใหม่** ทุกช่องได้ภาพเดียวกับที่เวทีส่งเข้ามา ทำแนวตั้งหรือลดบิตเรตเฉพาะช่องไม่ได้ ใช้ CPU ราว 11% ของ 1 คอร์ต่อช่อง
- **เน็ตขาออก** 4 ช่องใช้ 4 เท่าของบิตเรตเวที (5.5 Mbps ต่อช่อง = 22 Mbps) ส่งพร้อมกันได้ไม่เกิน `RESTREAM_MAX` ช่องรวมทุกเวที
  นับ Replay ที่กำลังส่งด้วย และระหว่างมี Restream อยู่จะเริ่ม Replay ใหม่ไม่ได้ ถ้าช่องไหนส่งไม่ทันเวลาจริง (ใน 60 วินาทีส่งได้น้อยกว่า 55 วินาที)
  ระบบจะตัดแล้วต่อใหม่ เพื่อไม่ให้ภาพที่ปลายทางแตก
- **อ่านสัญญาณเวทีแบบ SRT** เหมือนตัวบันทึก จึงคงจังหวะภาพกับเสียงตามเครื่องส่ง ถ้าเครื่องส่งมี timestamp ไม่เรียงจน MediaMTX ตัดการอ่านซ้ำ
  3 ครั้งใน 1 นาที ระบบจะสลับไปอ่านแบบ RTSP ให้เอง ภาพไม่ขาด แต่เสียงที่ปลายทางจะช้ากว่าภาพ 0.04–0.24 วินาที (วัด 10 พ.ย. 2026)
  และแถวจะบอกไว้ ควรแก้ที่เครื่องส่ง
- **แอปรีสตาร์ทกลางรายการ** ช่องที่กำลังส่งจะส่งต่อเอง ถ้าแอปหยุดไปไม่เกิน 10 นาทีและยังมี `RESTREAM_PIN` เกินนั้นจะไม่ส่งต่อ
  เพื่อไม่ให้ key ของเมื่อวานพาภาพซ้อมของวันนี้ออกช่องจริง
- **ต้นทางหลุดแล้ว ffmpeg ปิดการเชื่อมต่อแบบปกติ** แพลตฟอร์มที่ตั้งให้จบไลฟ์เมื่อสัญญาณหยุดจะจบทันที จึงต้องปิดตัวเลือกนั้นตามรายการด้านบน
- **Stream key** เก็บใน `/data/restream/<เวที>.json` (สิทธิ์ 0600) ไม่ลง log ไม่ส่งกลับมาที่หน้าเว็บ (เห็นแค่ 4 ตัวท้าย) แต่ root บน VM
  และคอนเทนเนอร์ทั้งสองอ่านไฟล์นี้ได้ และระหว่างส่ง key อยู่ในคำสั่ง ffmpeg ถ้าเปลี่ยน Server ต้องใส่ key ใหม่ด้วยเสมอ
- **ไม่มีสำรอง** เซิร์ฟเวอร์เครื่องเดียว ถ้าเครื่องหรือเน็ตมีปัญหา ทุกช่องหลุดพร้อมกัน และยังไม่มีการแจ้งเตือนออกนอกหน้าเว็บ

## ค่าตั้ง

| ค่า | ตั้งที่ | ความหมาย |
|---|---|---|
| ย้อนดูได้ (นาที) | หน้าเว็บ | ความยาวบัฟเฟอร์ระหว่างไลฟ์ ถ้าเปลี่ยนระหว่างไลฟ์ ตัวบันทึกจะเริ่มใหม่และภาพขาดไม่กี่วินาที |
| เก็บหลังจบไลฟ์ (ชม.) | หน้าเว็บ | บัฟเฟอร์ของไลฟ์ที่จบแล้วอยู่ให้ตัดคลิปต่อได้นานเท่านี้ |
| ดูช้ากว่าสด (วินาที) | หน้าเว็บ | เฉพาะตัวเล่นของแต่ละคน ไม่กระทบคนอื่น |
| `MIN_FREE_GB` | .env | ดิสก์ว่างต่ำกว่านี้ ระบบจะเริ่มลบบัฟเฟอร์เก่าก่อนเวลา |
| `RECONNECT_MIN` | .env | สัญญาณที่ต่อกลับภายในเวลานี้ จะต่อรอบเดิม ทั้ง dvr.sh และตัวกันดิสก์เต็มใช้ค่าเดียวกัน |
| `LOCAL_CLIP_HOURS` | .env | สำเนาคลิปบนเซิร์ฟเวอร์ ลบหลังจากนี้ เฉพาะคลิปที่อยู่บน Wasabi แล้ว |
| `CUT_WORKERS` | .env | จำนวนคลิปที่ตัดพร้อมกัน |
| `REPLAY_MAX` | .env | จำนวน replay ที่ส่งออกพร้อมกันได้ (ค่าเริ่มต้น 2) |
| `REPLAY_MAX_HOURS` | .env | replay หยุดเองเมื่อส่งครบกี่ชั่วโมง (ค่าเริ่มต้น 12) |
| `REPLAY_ALLOW_HOSTS` | .env | ชื่อเครื่องในวงภายในที่ยอมให้ replay และ restream ส่งไปได้ คั่นด้วยจุลภาค (ค่าเริ่มต้นว่าง = เฉพาะอินเทอร์เน็ต) |
| `RESTREAM_PIN` | .env | รหัสที่สองสำหรับสั่ง Restream 12 ตัวขึ้นไป ไม่ใช่ตัวเลขล้วน เว้นว่าง = ปิด Restream |
| `RESTREAM_MAX` | .env | จำนวนช่องที่ส่งพร้อมกันได้ รวมทุกเวทีและ Replay (ค่าเริ่มต้น 4) |
| `RESTREAM_SOURCE` | .env | เปลี่ยนที่อ่านสัญญาณเวที `{stage}` = ชื่อเวที ปกติไม่ต้องตั้ง (ค่าเริ่มต้นอ่าน SRT จาก MediaMTX) |

- **เก็บขั้นต่ำ 90 วัน** ไฟล์ที่ลบก่อน 90 วันยังคิดเงินจนครบ 90 วัน
- **ตัวอย่าง** คลิป 10 Mbps ยาว 1 นาทีใหญ่ราว 75 MB ถ้าตัดวันละ 100 คลิปจะได้ราว 7.5 GB ต่อวัน หรือราว 225 GB ต่อเดือน

## ข้อจำกัดที่รู้แล้ว

- **Wirecast ผ่านตัวรับแยก** ช่วงส่งต่อจาก relay เข้า MediaMTX ในเครื่องเดียวกันมีการส่งซ้ำแพ็กเก็ตบ้าง (loss ที่นับได้ราว 1%
  แต่ DROP = 0 และไฟล์ถอดรหัสสะอาดที่ 15 Mbps) เป็นเรื่องของจังหวะส่งของ ffmpeg ไม่ใช่ของหาย ถ้าวันหนึ่งเห็น DROP > 0 ค่อยดู
- **เวลาที่แสดง** มาจากนาฬิกาเซิร์ฟเวอร์ตอน ffmpeg เริ่มบันทึก ไม่ใช่เวลาของกล้อง อาจคลาดจากนาฬิกาจริงราว 1–2 วินาที
  ระบบตัดคลิปใช้เวลาชุดเดียวกับตัวเล่นทุกจุด คลิปจึงตรงกับที่เห็นบนจอเสมอ
- **ไลฟ์ต่อเนื่องเกิน 26 ชั่วโมงในรอบเดียว** timestamp ของ MPEG-TS จะวนรอบ ยังไม่ได้ทดสอบกรณีนี้
- **ไม่มีการเก็บไลฟ์เต็มขึ้น Wasabi อัตโนมัติ** ถ้าต้องการเก็บทั้งรอบ ให้ตั้ง In ที่ต้นรอบและ Out ที่ท้ายรอบ แล้วตัดเป็นคลิปเดียว

```bash
docker run --rm -v "$PWD/app":/app -w /app -e MEDIAMTX_API_PASS=x python:3.12-alpine sh -c 'python test_app.py && python test_janitor.py && python test_replay.py && python test_restream.py'
```

ทดสอบปลายทางด้วยตัวส่งปลอมและ S3 จำลอง ใช้ moto แทน Wasabi:

```bash
docker compose -p liveclip -f docker-compose.yml -f test/compose.test.yml up -d --build
docker compose -p liveclip exec -T web python -c "import app; app.s3_client().create_bucket(Bucket='liveclip-test')"
```

## บั๊กที่เคยเจอ ห้ามถอยกลับ

- **อย่าส่งสัญญาณซ้ำให้ ffmpeg ใน dvr.sh** MediaMTX ส่ง SIGINT ให้ทั้งกลุ่ม process อยู่แล้ว ถ้าส่งเพิ่มอีกครั้ง
  ffmpeg จะทิ้ง `index.m3u8` ไว้ศูนย์ไบต์ พอสัญญาณต่อกลับก็เริ่มรายการใหม่และบัฟเฟอร์เก่าหายทั้งหมด
- **อย่าใช้ `-ss` ฝั่งขาเข้ากับ concat demuxer** การ seek บน MPEG-TS กระโดดเลยไปหนึ่งไฟล์ย่อย
  ทำให้คลิปเริ่มช้ากว่าจริงหนึ่งวินาที ทั้งที่ความยาวคลิปยังถูก ถ้าเช็กแค่ความยาวจะจับไม่ได้
- **MediaMTX ไม่รอ hook ตัวเก่าปิดก่อนเริ่มตัวใหม่** dvr.sh จึงต้องรอ lock ต่อสัญญาณ
  ไม่อย่างนั้นตอนต่อกลับเร็ว ๆ จะมี ffmpeg สองตัวเขียนโฟลเดอร์เดียวกัน busybox `flock` ไม่มี `-w` ต้องวนรอด้วย `-n`
- **อย่า mount ไฟล์เดี่ยวเข้าคอนเทนเนอร์** โปรแกรมแก้ไฟล์ส่วนใหญ่เซฟด้วยการเขียนไฟล์ใหม่ทับ mount แบบไฟล์เดี่ยวจะยังชี้ไฟล์ตัวเก่าที่ถูกลบ
  MediaMTX เคยหา dvr.sh ไม่เจอและหยุดบันทึกเพราะเรื่องนี้ ตอนนี้จึงอบค่าตั้งไว้ในอิมเมจแทน
- **ห้ามตั้ง `udpReadBufferSize` เกิน rmem_max ของโฮสต์** MediaMTX จะไม่เปิดพอร์ต SRT เลย ไม่ใช่แค่ลดค่าให้ (ทดลองแล้ว 26 ต.ค.)
- **MediaMTX ไม่ใช่ init** ต้องมี `init: true` ใน compose ไม่อย่างนั้น process ของ hook ที่จบแล้วค้างเป็น zombie ไปเรื่อย ๆ
