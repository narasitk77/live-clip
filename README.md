# Live Clip

รับสัญญาณไลฟ์ SRT จาก vMix / Wirecast นอกสถานที่ เก็บเป็นบัฟเฟอร์ย้อนหลังบนเซิร์ฟเวอร์
ให้ทีมตัดเปิดดูในเบราว์เซอร์ระหว่างไลฟ์ ตั้งจุด In/Out แล้วได้คลิป MP4 ไปตัดต่อด้วยโปรแกรมอะไรก็ได้
คลิปที่ตัดแล้วเก็บขึ้น Wasabi

```
vMix / Wirecast ──SRT (UDP 8890, มี passphrase)──▶ MediaMTX ──▶ dvr.sh (ffmpeg)
                                                                 │ บัฟเฟอร์ HLS ไฟล์ละ 2 วิ
                                                                 ▼
                         เบราว์เซอร์ทีมตัด ◀── web (app.py) ──▶ ffmpeg ตัดคลิป ──▶ Wasabi
```

- **บัฟเฟอร์อยู่บนดิสก์เซิร์ฟเวอร์เท่านั้น** ไม่ขึ้น Wasabi เพราะ Wasabi คิดเงินขั้นต่ำ 90 วันต่อไฟล์
  บัฟเฟอร์ที่เขียนแล้วลบทุกไม่กี่ชั่วโมงจะโดนคิดเงินเต็ม 90 วันทุกไฟล์
- **ขึ้น Wasabi เฉพาะคลิปที่ตัดแล้ว** ลิงก์ดาวน์โหลดสร้างใหม่ทุกครั้งที่กด จึงไม่มีวันหมดอายุในหน้าเว็บ
- **คลิปโหลดจากเซิร์ฟเวอร์ได้ทันที** ตั้งแต่ตัดเสร็จ ไม่ต้องรออัป Wasabi
  ถ้าอัปพลาด คลิปจะขึ้นว่า "ล้มเหลว" พร้อมสาเหตุ ยังโหลดจากเซิร์ฟเวอร์ได้ และกด "ลองใหม่" ได้

## สิ่งที่ต้องเตรียมก่อนขึ้นใช้งานจริง

| เรื่อง | ใครทำ | รายละเอียด |
|---|---|---|
| เครื่องที่จะรัน | นัท | โฮสต์ Docker ตัวไหนก็ได้ ดิสก์ว่างพอสำหรับบัฟเฟอร์ ดูตารางด้านล่าง |
| เปิดพอร์ต | IT | forward **UDP 8890** จากอินเทอร์เน็ตเข้าเครื่องนี้ |
| โดเมน + HTTPS | นัท | ชี้โดเมนผ่าน Nginx Proxy Manager มาที่พอร์ตเว็บ 8080 |
| Wasabi | นัท | สร้าง bucket ใน region ap-southeast-1 Singapore + access key ชุดใหม่ที่เขียนได้เฉพาะ bucket นี้ |
| Wasabi lifecycle | นัท | เปิด "Delete incomplete multipart uploads" ไว้ กันชิ้นอัปค้างโดนคิดเงิน |
| passphrase SRT | นัท | สุ่ม 32–64 ตัวอักษร ห้ามเกิน 79 เพราะ MediaMTX รับได้แค่นั้น แต่ vMix/Wirecast รับได้ 80 |
| รหัสอื่น ๆ | นัท | `WEB_PASSWORD` 12 ตัวขึ้นไป และ `MEDIAMTX_API_PASS` สุ่มอะไรก็ได้ ใช้คุยกันระหว่างสองคอนเทนเนอร์ |

พื้นที่ดิสก์ที่บัฟเฟอร์ใช้ คิดที่ 10 Mbps:

| ย้อนดูได้ | 1 สัญญาณ | 2 สัญญาณ | 4 สัญญาณ |
|---|---|---|---|
| 1 ชม. | 4.5 GB | 9 GB | 18 GB |
| 2 ชม. | 9 GB | 18 GB | 36 GB |
| 6 ชม. | 27 GB | 54 GB | 108 GB |

บัฟเฟอร์ของไลฟ์ที่จบแล้วจะอยู่ต่อตามค่า "เก็บหลังจบไลฟ์" แล้วลบเอง
ถ้าดิสก์ว่างต่ำกว่า `MIN_FREE_GB` ระบบจะลบบัฟเฟอร์ของไลฟ์ที่จบแล้วก่อนเวลา โดยเริ่มจากเก่าสุด
และขึ้นแถบเตือนในหน้าเว็บว่าลบรอบไหนไป ระบบจะไม่ลบบัฟเฟอร์ของไลฟ์ที่กำลังสด
และไม่ลบรอบที่สัญญาณเพิ่งหลุดไม่ถึง `RECONNECT_MIN` นาที เพราะตัวส่งอาจต่อกลับมา

โหมดเก็บคลิปในเครื่อง คือไม่ได้ตั้ง Wasabi คลิปจะไม่ถูกลบอัตโนมัติเลย เพราะเป็นสำเนาเดียว ต้องลบเอง

## รันในเครื่อง (ทดสอบ)

```bash
cp .env.example .env      # แล้วกรอกค่าจริง
docker compose up -d --build
```

`docker-compose.yml` build อิมเมจทั้งสองตัวจากโฟลเดอร์นี้ ค่าตั้ง MediaMTX กับ dvr.sh ถูกอบไว้ในอิมเมจ

## ขึ้น Portainer (เครื่องจริง)

โฮสต์คือ NAS RackStation ตัวเดียวกับ probook มี Docker, Nginx Proxy Manager (stack `management`) และดิสก์ว่างหลายสิบ TB

1. **โค้ดอยู่ในรีโป GitHub `narasitk77/live-clip`** ทุก push ขึ้น `main` จะ build อิมเมจ 2 ตัวขึ้น GHCR
   คือ `live-clip-web` และ `live-clip-mediamtx` แท็ก `latest` และ `sha-<commit>`
2. **stack ใน Portainer** ชื่อ `live-clip` (id 156, สร้าง 26 ต.ค. 2026) แบบ git-backed ชี้รีโปนี้ compose path = `docker-compose.portainer.yml`
   env ของ stack มาจากไฟล์ `.env.portainer` บนเครื่องนัท (ไม่ขึ้น git, มี `IMAGE_TAG=sha-<commit>`, รหัสทุกตัว,
   `SRT_PUBLIC_HOST=thestandard.fortiddns.com`, `MIN_FREE_GB=200`, `CUT_WORKERS=1` และค่า S3 ถ้ามี)
   สร้าง/ปรับด้วย `python3 scripts/portainer_stack.py create|redeploy <tag>|status|logs` สคริปต์เช็กว่าคอนเทนเนอร์รันแท็กที่ขอจริง
3. **เว็บไม่เปิดพอร์ตบนโฮสต์** NPM อยู่บนเครือข่าย `management_default` เดียวกัน (ทดสอบแล้วว่า NPM เรียก `live-clip-web:8080` ถึง)
   หลัง IT เพิ่ม DNS `liveclip.thestandard.co` แล้ว ให้เพิ่ม Proxy Host ใน NPM ตามนี้

   | ช่อง | ค่า |
   |---|---|
   | Domain Names | liveclip.thestandard.co |
   | Scheme | http |
   | Forward Hostname / IP | live-clip-web |
   | Forward Port | 8080 |
   | Block Common Exploits | เปิด |
   | Websockets Support | ไม่ต้อง |
   | SSL | ขอ Let's Encrypt ใหม่ หรือใช้ใบเดียวกับ probook ถ้าเป็น wildcard, เปิด Force SSL |

   วง LAN ของ NAS (192.168.21.x) เข้าจากวงออฟฟิศไม่ได้ จึงไม่มีทางลัดก่อนมีโดเมน
   ตรวจ: `curl -su editor:<รหัส> https://liveclip.thestandard.co/api/state` ต้องได้ JSON ที่มี `"storage": "local"`
4. **IT ต้อง forward UDP 8890 และ UDP 8891** จาก FortiGate มาที่ NAS 8890 = vMix/OBS (ตั้งชื่อสัญญาณเองได้หลายตัว), 8891 = Wirecast
5. **deploy รอบถัดไป** = push ขึ้น main รอ CI เสร็จ (`gh run watch`) แล้ว `python3 scripts/portainer_stack.py redeploy sha-<commit>`
   คำสั่งนี้ส่ง env จาก `.env.portainer` ไปด้วยทุกครั้ง จึงใช้เปลี่ยนรหัสหรือเปิด Wasabi ได้ด้วย
   กับดักเดียวกับ probook คือ redeploy โดยไม่เปลี่ยน IMAGE_TAG จะได้อิมเมจเดิม
6. **ทดสอบว่าพอร์ตเปิดถึงแล้ว** รัน `test/probe_prod.sh` จากเครื่องไหนก็ได้ที่มี Docker แล้วดู `logs mediamtx`
   ต้องเห็น `publishing to path 'probe1'` ถ้าขึ้น I/O error แปลว่า UDP 8890 ยังมาไม่ถึง NAS (26 ต.ค. ยังไม่ถึง)

ยังไม่ตั้ง Wasabi ก็ขึ้นได้ ระบบจะเก็บคลิปไว้บน NAS อย่างเดียว ใส่ค่า S3 ทั้งสี่ตัวแล้ว redeploy เมื่อไหร่ก็เปลี่ยนเป็น Wasabi

- **หน้าเว็บ** ผูกกับ `127.0.0.1` ของเครื่องเท่านั้น เข้าจากเครื่องอื่นตรง ๆ ไม่ได้ ต้องผ่าน HTTPS ของ Nginx Proxy Manager
  ห้ามตั้ง `WEB_BIND` เป็น `0.0.0.0` เพราะรหัสผ่านจะวิ่งเป็น HTTP เปล่า
- **ล็อกอิน** ใช้ `WEB_USER` / `WEB_PASSWORD`
- **ค่าบังคับ** ถ้ารหัสไม่ครบ ยังเป็นค่าตัวอย่าง หรือตั้ง Wasabi ไม่ครบทั้งสี่ค่า ระบบจะไม่ยอมเริ่มและบอกว่าขาดอะไร
- **โหมดเก็บในเครื่อง** ถ้าปล่อยค่า S3 ว่างทั้งหมด แอปจะเก็บคลิปไว้บนเซิร์ฟเวอร์อย่างเดียว
- **endpoint ของ Wasabi** ต้องตรงกับ region ของ bucket ถ้าผิด region อ่านไฟล์ได้แต่เขียนไม่ได้ อาการนี้หลอกว่าระบบปกติ

## ตั้งค่าตัวส่ง

ทั้งสองโปรแกรมใช้ค่าชุดเดียวกัน

| ช่อง | ค่า |
|---|---|
| โหมด | Caller |
| Address / Hostname | ที่อยู่สาธารณะของเซิร์ฟเวอร์ ค่า `SRT_PUBLIC_HOST` |
| Port | 8890 |
| Stream ID | `publish:<ชื่อสัญญาณ>` เช่น `publish:cam1` ใช้ตัวเล็ก ตัวเลข `-` `_` ยาวไม่เกิน 32 ตัว |
| Passphrase | ค่า `SRT_PASSPHRASE` |
| วิดีโอ | H.264 เท่านั้น ห้าม HEVC เพราะเบราว์เซอร์เล่นไม่ได้ทุกตัว |
| เสียง | AAC สเตอริโอ แทร็กเดียว ใน vMix ห้ามเปิด "Split Stereo Pairs into Separate Tracks" |
| Keyframe | ทุก 1–2 วินาทีแบบคงที่ ใน vMix คือช่อง "Keyframe Frequency (seconds)" |
| Bitrate | ถ้าอัปโหลดหน้างานได้ 10 Mbps ให้ตั้งรวมราว **6 Mbps** เพราะ SRT ต้องเผื่อส่งซ้ำอีกราว 25% |

- **vMix** ตั้งที่ Settings > Outputs > ปุ่มฟันเฟือง > SRT ช่อง Latency ให้ตั้ง 500–1000 ms สำหรับเน็ตในประเทศ
  ค่านี้ฝั่งเซิร์ฟเวอร์ใช้ตามที่ vMix ส่งมา ช่อง Key Length ตั้ง 16, 24 หรือ 32 ก็ได้
- **Wirecast** ตั้งที่ Output > Output Settings > SRT แต่ให้ส่งเข้า **พอร์ต 8891** แทน 8890 และไม่ต้องใส่ Stream ID
  เพราะ Wirecast ไม่มีช่องตั้ง latency พอร์ต 8891 คือตัวรับแยก (`relay-wirecast`) ที่เราตั้ง latency ให้เอง
  ค่าเริ่มต้น 1000 ms (`WIRECAST_LATENCY_MS`) สัญญาณจะโผล่ในหน้าเว็บชื่อ `wirecast1` (`WIRECAST_NAME`)
  ตัวรับนี้รับ Wirecast ได้ทีละเครื่อง ถ้ามีเครื่องที่สองให้ก๊อปบล็อก `relay-wirecast` ใน compose เป็นพอร์ต 8892 และชื่อใหม่

ถ้าส่งชื่อเดียวกันจากสองเครื่องพร้อมกัน เครื่องหลังจะเตะเครื่องแรกออก ดังนั้นต้องตั้งชื่อสัญญาณไม่ซ้ำกันต่อเครื่อง

## วิธีใช้ (ทีมตัด)

1. เลือกสัญญาณทางซ้าย จุดเขียวแปลว่ารับสัญญาณอยู่ จุดแดงแปลว่ากำลังบันทึกบัฟเฟอร์
2. เลื่อนแถบเวลาย้อนดู หรือกด "ไปที่สด" ช่อง "ดูช้ากว่าสด" ใช้ดูตามหลังสดตามจำนวนวินาทีที่ตั้ง
3. กด `I` ตั้งจุดเริ่ม กด `O` ตั้งจุดจบ แล้วปรับละเอียดด้วยปุ่ม ±1 วิ และ ±0.1 วิ ปุ่ม "ไปดู" พาไปเช็กภาพตรงจุดนั้น
4. ตั้งชื่อ เลือกโหมด แล้วกด "สร้างคลิป"
   - **เร็ว** ไม่เข้ารหัสใหม่ เสร็จในไม่กี่วินาที คลิปอาจเริ่มก่อน In ไม่เกินราว 2 วินาที แต่ไม่มีวันเริ่มช้ากว่า In
   - **ตรงเฟรม** เข้ารหัสใหม่ เริ่มและจบตรงเฟรม ช้ากว่าและกิน CPU เซิร์ฟเวอร์
5. กด "ดาวน์โหลด" ในรายการคลิป

ถ้าสัญญาณหลุดแล้วต่อกลับภายใน 10 นาที ระบบจะต่อรอบเดิมให้ คลิปที่คร่อมช่วงสัญญาณขาดจะบอกว่าภาพขาดไปกี่วินาที
ตรงจุดต่อกลับ ภาพจะค้างราว 2 วินาทีขณะที่เสียงเดินต่อ เพราะเสียงมาถึงก่อนภาพ keyframe แรก
โหมดตรงเฟรมเติมเฟรมซ้ำให้ ไฟล์จึงเป็น frame rate คงที่ ใช้กับ Premiere ได้

## ค่าใช้จ่าย Wasabi (ราคา ต.ค. 2026)

- **ค่าพื้นที่** $7.99 ต่อ TB ต่อเดือน ขั้นต่ำคิดที่ 1 TB ต่อเดือน
- **ค่าโหลดออกและค่า API** ไม่คิด ตราบที่ปริมาณโหลดออกต่อเดือนไม่เกินปริมาณที่เก็บไว้
- **เก็บขั้นต่ำ 90 วัน** ไฟล์ที่ลบก่อน 90 วันยังคิดเงินจนครบ 90 วัน
- **ตัวอย่าง** คลิป 10 Mbps ยาว 1 นาทีใหญ่ราว 75 MB ถ้าตัดวันละ 100 คลิปจะได้ราว 7.5 GB ต่อวัน หรือราว 225 GB ต่อเดือน

## ข้อจำกัดที่รู้แล้ว

- **Wirecast ผ่านตัวรับแยก** ช่วงส่งต่อจาก relay เข้า MediaMTX ในเครื่องเดียวกันมีการส่งซ้ำแพ็กเก็ตบ้าง (loss ที่นับได้ราว 1%
  แต่ DROP = 0 และไฟล์ถอดรหัสสะอาดที่ 15 Mbps) เป็นเรื่องของจังหวะส่งของ ffmpeg ไม่ใช่ของหาย ถ้าวันหนึ่งเห็น DROP > 0 ค่อยดู
- **เวลาที่แสดง** มาจากนาฬิกาเซิร์ฟเวอร์ตอน ffmpeg เริ่มบันทึก ไม่ใช่เวลาของกล้อง อาจคลาดจากนาฬิกาจริงราว 1–2 วินาที
  ระบบตัดคลิปใช้เวลาชุดเดียวกับตัวเล่นทุกจุด คลิปจึงตรงกับที่เห็นบนจอเสมอ
- **ไลฟ์ต่อเนื่องเกิน 26 ชั่วโมงในรอบเดียว** timestamp ของ MPEG-TS จะวนรอบ ยังไม่ได้ทดสอบกรณีนี้
- **ไม่มีการเก็บไลฟ์เต็มขึ้น Wasabi อัตโนมัติ** ถ้าต้องการเก็บทั้งรอบ ให้ตั้ง In ที่ต้นรอบและ Out ที่ท้ายรอบ แล้วตัดเป็นคลิปเดียว

ทดสอบปลายทางด้วยตัวส่งปลอมและ S3 จำลอง ใช้ moto แทน Wasabi:

```bash
docker compose -p liveclip -f docker-compose.yml -f test/compose.test.yml up -d --build
docker compose -p liveclip exec -T web python -c "import app; app.s3_client().create_bucket(Bucket='liveclip-test')"
set -a; . ./.env; set +a; test/pub.sh cam1
docker compose -p liveclip cp test/e2e_check.py web:/app/e2e_check.py
docker compose -p liveclip exec -T web python /app/e2e_check.py
```

`e2e_check.py` เทียบภาพจริงด้วย PSNR ว่าเฟรมแรกและเฟรมสุดท้ายของคลิปตรงกับจุด In/Out
และเทียบว่าไฟล์บน S3 ตรงกับในเครื่องทุกไบต์

## บั๊กที่เคยเจอ ห้ามถอยกลับ

- **อย่าส่งสัญญาณซ้ำให้ ffmpeg ใน dvr.sh** MediaMTX ส่ง SIGINT ให้ทั้งกลุ่ม process อยู่แล้ว ถ้าส่งเพิ่มอีกครั้ง
  ffmpeg จะทิ้ง `index.m3u8` ไว้ศูนย์ไบต์ พอสัญญาณต่อกลับก็เริ่มรายการใหม่และบัฟเฟอร์เก่าหายทั้งหมด
- **อย่าใช้ `-ss` ฝั่งขาเข้ากับ concat demuxer** การ seek บน MPEG-TS กระโดดเลยไปหนึ่งไฟล์ย่อย
  ทำให้คลิปเริ่มช้ากว่าจริงหนึ่งวินาที ทั้งที่ความยาวคลิปยังถูก ถ้าเช็กแค่ความยาวจะจับไม่ได้
- **MediaMTX ไม่รอ hook ตัวเก่าปิดก่อนเริ่มตัวใหม่** dvr.sh จึงต้องรอ lock ต่อสัญญาณ
  ไม่อย่างนั้นตอนต่อกลับเร็ว ๆ จะมี ffmpeg สองตัวเขียนโฟลเดอร์เดียวกัน busybox `flock` ไม่มี `-w` ต้องวนรอด้วย `-n`
- **อย่า mount ไฟล์เดี่ยวเข้าคอนเทนเนอร์** โปรแกรมแก้ไฟล์ส่วนใหญ่เซฟด้วยการเขียนไฟล์ใหม่ทับ mount แบบไฟล์เดี่ยวจะยังชี้ไฟล์ตัวเก่าที่ถูกลบ
  MediaMTX เคยหา dvr.sh ไม่เจอและหยุดบันทึกเพราะเรื่องนี้ ตอนนี้จึงอบค่าตั้งไว้ในอิมเมจแทน
- **ห้ามตั้ง `udpReadBufferSize` เกิน rmem_max ของโฮสต์** MediaMTX จะไม่เปิดพอร์ต SRT เลย ไม่ใช่แค่ลดค่าให้ (ทดลองแล้ว 26 ต.ค.)
- **MediaMTX ไม่ใช่ init** ต้องมี `init: true` ใน compose ไม่อย่างนั้น process ของ hook ที่จบแล้วค้างเป็น zombie ไปเรื่อย ๆ
